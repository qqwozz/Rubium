
# Rubium — Version Control для совместных тетрадей

> Спецификация механик версионирования, fork и merge для coop-тетрадей.

## 1. Контекст

Rubium — платформа для учебных конспектов. Мы хотим дать пользователям **механики GitHub** (fork, version control, diff, merge) в **простой форме**, понятной обычному студенту, а не разработчику.

**Ключевое отличие от Git:**

- Не DAG коммитов, не SHA-хеши, не branching.
- Только то, что нужно для совместной работы над учебным конспектом.
- Простая, но надёжная механика без потери данных.

---

## 2. Основные понятия

| Термин                         | Значение                                                                                   |
| ------------------------------------ | -------------------------------------------------------------------------------------------------- |
| **Тетрадь (notebook)**  | Учебный конспект. Основная единица контента.                 |
| **Страница (page)**    | Подраздел тетради. Редактируется отдельно.                    |
| **Соавтор (co-author)** | Пользователь с правами на редактирование тетради.       |
| **Версия (version)**     | Уникальный ID текущего контента страницы.                        |
| **Fork**                       | Копия тетради другого автора, связанная с оригиналом. |
| **Diff**                       | Показ различий между двумя версиями страницы.               |
| **Merge**                      | Объединение изменений двух авторов в одну страницу.    |

## 3. Модель данных

### 3.1. Таблица `notebooks` — добавления

```sql
ALTER TABLE notebooks
ADD COLUMN content_id UUID DEFAULT gen_random_uuid(),
ADD COLUMN previous_content_id UUID,
ADD COLUMN previous_content JSONB,
ADD COLUMN content_updated_at TIMESTAMPTZ DEFAULT NOW(),
ADD COLUMN content_updated_by UUID REFERENCES rubium_users(id);
```

**Назначение:**

- `content_id` — уникальный ID текущего контента.
- `previous_content_id` — ID предыдущей версии.
- `previous_content` — контент предыдущей версии (для merge и diff).
- `content_updated_at` — время последнего сохранения.
- `content_updated_by` — кто последний сохранил.

### 3.2. Таблица `notebook_authors` — соавторы

```sql
CREATE TABLE notebook_authors (
  notebook_id UUID REFERENCES notebooks(id) ON DELETE CASCADE,
  user_id UUID REFERENCES rubium_users(id) ON DELETE CASCADE,
  role TEXT CHECK (role IN ('owner', 'editor', 'viewer')),
  invited_by UUID REFERENCES rubium_users(id),
  invited_at TIMESTAMPTZ DEFAULT NOW(),
  accepted_at TIMESTAMPTZ,
  PRIMARY KEY (notebook_id, user_id)
);
```

**Роли:**

- `owner` — создатель, может удалять, приглашать, менять роли.
- `editor` — может редактировать контент.
- `viewer` — только чтение.

### 3.3. Таблица `notebook_forks` — связи fork

```sql
CREATE TABLE notebook_forks (
  fork_id UUID PRIMARY KEY REFERENCES notebooks(id) ON DELETE CASCADE,
  original_id UUID REFERENCES notebooks(id) ON DELETE SET NULL,
  forked_by UUID REFERENCES rubium_users(id),
  forked_at TIMESTAMPTZ DEFAULT NOW()
);
```

**Назначение:** отслеживание линии fork'ов. Fork не связан с версиями, только с оригиналом.

## 4. Механика 1 — Optimistic Concurrency (защита от конфликтов)

### 4.1. Принцип

Каждый раз при сохранении страницы автор передаёт **ID версии, которую он загрузил**. Backend проверяет: не изменилась ли версия с момента загрузки. Если да — конфликт (409).

### 4.2. Сценарий

1. Иван открывает страницу. `content_id = A`.
2. Маша открывает ту же страницу. `content_id = A`.
3. Маша сохраняет. Backend: `A → B`. Успех.
4. Иван сохраняет. Backend: `WHERE content_id = A` — не совпадает (там уже `B`).
5. Backend возвращает **409 Conflict** с текущим контентом (`B`) и `content_id = B`.
6. Frontend показывает диалог: «Маша изменила страницу. Что делать?»

### 4.3. API

**PATCH `/notebooks/:id/pages/:page_id`**

Request:

```json
{
  "content": "...",
  "base_content_id": "uuid"
}
```

Response 200 OK:

```json
{
  "content_id": "new-uuid",
  "updated_at": "2026-09-15T10:00:00Z"
}
```

Response 409 Conflict:

```json
{
  "conflict": true,
  "server_content": "...",
  "server_content_id": "current-uuid",
  "server_updated_by": {"id": "...", "name": "Маша"}
}
```

### 4.4. Frontend UX

При получении 409:

- **Никакой автоматической перезагрузки.**
- Показывается модалка:

```
⚠️ Конфликт версий

Маша изменила эту страницу, пока вы писали.

Ваша версия: 12 правок
Версия Маши: 5 правок

[Сравнить]  [Отменить мои]  [Перезаписать]
```

- **«Перезаписать»** → PATCH с `base_content_id = server_content_id`, `content = local_content`. Ваши правки побеждают.
- **«Отменить мои»** → страница обновляется контентом Маши. Ваши правки теряются (по вашему решению).
- **«Сравнить»** → diff-view (см. раздел 5).

## 5. Механика 2 — Diff

### 5.1. Принцип

Показ различий между **двумя версиями** страницы. Используется в двух случаях:

1. При конфликте (409).
2. При просмотре истории (если пользователь сам запрашивает).

### 5.2. Технически

- **Библиотека:** `jsdiff` (frontend) или `diff-match-patch` (универсально).
- **Формат:** word-level diff для текста, block-level для HTML.
- **Представление:** two-column или inline.

### 5.3. UX

**Inline-режим (простой):**

```
Производная — это <del>предел отношения</del><ins>отношение приращений</ins>...
```

**Side-by-side (продвинутый):**

```
Ваша версия              |  Версия Маши
Производная — это         |  Производная — это
предел отношения...       |  отношение приращений...
```

**Цвета:**

- Красный — удалено.
- Зелёный — добавлено.
- Серый — без изменений.

## 6. Механика 3 — Merge

### 6.1. Три уровня сложности

**Уровень 1 — Выбор версии (MVP).**

- «Мою» / «Чужую».
- Не настоящий merge.
- Теряешь либо свои, либо чужие правки.
- **Реализация:** 1 день.

**Уровень 2 — Блочный merge (V2).**

- Разбить контент на блоки (по HTML-тегам: `<p>`, `<h2>`, `<pre>`, `<table>`).
- Показать изменения блоками.
- Пользователь выбирает: «Оставить моё / Чужое» для каждого блока.
- **Реализация:** 1–2 недели.

**Уровень 3 — 3-way merge (V3).**

- Base (общий предок) + Yours + Theirs.
- Автоматически объединяет непересекающиеся изменения.
- Конфликты помечает и просит выбрать.
- **Реализация:** 1–2 месяца.

### 6.2. Для 3-way merge нужна базовая версия

**Обязательно хранить:**

- `previous_content` — предыдущая версия (общий предок).
- `content` — текущая версия.
- `local_content` — версия пользователя (на frontend).

**Алгоритм:**

1. Diff `previous_content` vs `content` → изменения автора 1.
2. Diff `previous_content` vs `local_content` → изменения автора 2.
3. Если изменения **не пересекаются** — авто-merge.
4. Если пересекаются — показать конфликт, дать пользователю выбрать.

### 6.3. Библиотеки

- **`node-diff3`** — 3-way merge для текста.
- **`diff3`** — Node.js.
- **`jsdiff`** — diff.
- **`diff-match-patch`** — Google's diff/patch/merge.

### 6.4. UX 3-way merge

```
Конфликт в блоке 3 из 12

Базовая версия:    Производная — это предел...
Ваша версия:       Производная — это предел отношения...
Версия Маши:       Производная — это отношение...

[Оставить моё]  [Оставить чужое]  [Объединить вручную]
```

## 7. Механика 4 — Fork

### 7.1. Принцип

Fork — копия чужой тетради. Создаётся одним нажатием. Связь с оригиналом сохраняется.

### 7.2. Сценарий

1. Иван публикует тетрадь «Матан для 1 курса».
2. Маша нажимает «Форкнуть».
3. Создаётся копия с названием «Матан для 1 курса (от Ивана)».
4. Маша редактирует свою копию.
5. Оригинал не меняется.
6. В её тетради показывается: «Forked from @ivan».
7. Иван видит: «Эту тетрадь форкнули 5 раз».

### 7.3. API

**POST `/notebooks/:id/fork`**

Response:

```json
{
  "new_notebook_id": "uuid",
  "original_id": "uuid",
  "forked_at": "2026-09-15T10:00:00Z"
}
```

### 7.4. UX

- Кнопка «Форкнуть» на странице публичной тетради.
- Показ lineage: «Forked from @ivan · 5 forks».
- Возможность посмотреть «Все форки» (список).

## 8. Приоритеты реализации

### MVP (2–4 недели)

- [ ] `content_id` + optimistic concurrency.
- [ ] 409 при конфликте.
- [ ] Диалог: «Мою / Чужую».
- [ ] Базовая защита от потери данных.

### V2 (1–2 месяца)

- [ ] `previous_content` в БД.
- [ ] Diff (библиотека `jsdiff`).
- [ ] UI diff при конфликте.
- [ ] Блочный merge.

### V3 (3–6 месяцев)

- [ ] 3-way merge (библиотека `node-diff3`).
- [ ] UI 3-way merge.
- [ ] Fork-механика.
- [ ] Публичные профили fork.

### V4 (6+ месяцев)

- [ ] Real-time sync (Yjs + WebSocket).
- [ ] Курсоры других пользователей.
- [ ] Live-редактирование.

## 9. Что НЕ делать

- **Не пиши свой diff-алгоритм.** Используй `jsdiff` или `diff-match-patch`.
- **Не пиши свой merge-алгоритм.** Используй `node-diff3` или `diff3`.
- **Не делай Git под капотом.** Не нужен DAG коммитов, SHA, branching.
- **Не делай real-time sync сразу.** Это +2–3 месяца работы (Yjs, WebSocket, CRDT).
- **Не храни всю историю версий.** Только текущую и предыдущую.

---

## 10. Правила работы

1. **Данные пользователя не теряются молча.** Всегда даём выбор.
2. **Простота важнее полноты.** Студенту не нужен Git. Нужен рабочий merge.
3. **Начинаем с MVP.** Оптимистичный контроль версий — самое главное.
4. **Diff и merge — по мере роста.** Не раньше, чем 1000 активных юзеров.
5. **Fork — после MVP.** Fork — это виральность, но не защита данных.

---

## 11. Метрики

- **Конфликты в день** (сколько раз 409).
- **Разрешения конфликтов** (перезапись / отмена / merge).
- **Потерянные правки** (должно быть 0).
- **Fork rate** (сколько тетрадей форкают).
- **Coop-тетради** (% от общего числа).
